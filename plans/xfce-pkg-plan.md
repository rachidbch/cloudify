# Plan: pkg/xfce (XFCE + xrdp GUI guest)

Status: drafted (guacamole plan archived 2026-09-07, shipped + green; xfce is the current unit), pending human consent before any code (cloudify CRITICAL GATE).
Grounded in: plans/guacamole-pkg-description.md (mechanism description, gate artifact,
applies unchanged - same sourced-recipe/shadows/verify contract proven by pkg/guacamole),
.drafts/xfce-guacamole-sop.md (Package 1), and the live xfce oracle (cloudstation:guac-gui).

## Human decisions (Rachid, 2026-09-07)

1. Test target: disposable scratch guest on node cloudai (no nesting needed, xrdp runs
   unprivileged in Incus; guac-gui proves the pattern).
2. Usernames are human-given; passwords are auto-generated by the package and printed to
   the human once. (Supersedes the SOP draft's CLOUDIFY_XFCE_USER_PASSWORD-required input.)
3. Production oracle (cloudstation:guac-gui + the cloudstation guacamole stack) stays as-is;
   the pkgs are for future installs only. Never test/destroy against it.

## Boundary

pkg/xfce installs and configures the graphical desktop endpoint inside an Ubuntu 24.04
guest. Owns: XFCE, XRDP, Xorg integration, the GUI login account (+ generated password),
the XFCE session command, Chrome, helpers.rc, the XRDP service.
Does NOT own: Incus, Tailscale identity/tags, ACLs, UFW forwarding, guacamole, or the
guacamole connection record (guacamole pkg owns that, driven by config vars).

## Oracle-first (ground truth before code - post-mortem rule)

Read the live oracle read-only and record facts into a fact-source table BEFORE writing any
recipe line. Targets on cloudstation:guac-gui (via ssh, tailnet only):
- installed package list (xfce4, xfce4-goodies, xrdp, xorgxrdp, dbus-x11, chrome)
- /home/gui/.xsession content, /home/gui/.config/xfce4/helpers.rc
- xrdp service state, /etc/xrdp/key.pem perms + ownership, ssl-cert group
- how Chrome was installed (.deb path) and its user registration
- gui user creation facts (shell, home, group)
Each constant (package names, session cmd, key.pem mode, helpers.rc line, chrome URL) gets a
row: value + source (guac-gui state or upstream doc fetched via exa). Recipe is written only
after the table is complete. Known from the SOP already (to confirm, not assume):
startxfce4, key.pem readable via ssl-cert, Chrome from dl.google.com .deb, helpers.rc
WebBrowser=google-chrome, .xsession owned by the user.

## Inputs

- CLOUDIFY_XFCE_USER, human-given, default gui.
- CLOUDIFY_XFCE_SESSION, default startxfce4.
- CLOUDIFY_XFCE_RDP_PORT, default 3389.
- CLOUDIFY_XFCE_INSTALL_CHROME, default true; CLOUDIFY_XFCE_CHROME_URL default the Google .deb.
- No password input: generated on user creation.

## Password model (decision 2)

- Generate at user creation on the guest: 24+ chars, URL-safe alphabet only (no single
  quotes/control chars - payload landmine L1; the value later crosses the payload into
  guacamole config).
- Persist on the guest: mode-600 file (e.g. /etc/cloudify/xfce-user.env) so reruns never
  regenerate (normal rerun preserves the password; force reinstall preserves it too unless
  --clear-data, which is destructive by design).
- Print ONCE at creation with a clear banner in the install output. That printed value is
  the handoff: the orchestrator reads it from the log and sets it as
  CLOUDIFY_GUACAMOLE_RDP_PASSWORD (deployment store or pkgs/guacamole.yaml) before running
  `cloudify configure guacamole`.
- Loss recovery documented: read the mode-600 file on the guest (ssh as root).
- gui stays non-sudo by default (SOP package default; the live oracle's sudo is an
  instance-specific deviation, not a package default).

## Install sequence (draft, to be confirmed against the fact table)

1. pkg_apt_install xfce4 xfce4-goodies xrdp xorgxrdp dbus-x11 (+ oracle-confirmed set).
2. Create user when absent (human-given name, home, non-root shell); generate + persist +
   print password at creation only.
3. Write ~/.xsession (session command, user-owned); helpers.rc WebBrowser=google-chrome.
4. Fix /etc/xrdp/key.pem perms (ssl-cert group readable), add xrdp to ssl-cert, restart xrdp,
   enable + start service.
5. Chrome .deb install + register as user's http/https/html handler (oracle-confirmed path).
6. Install guard: skip when healthy and FORCE/CLEAR_DATA empty. CLEAR_DATA wipes only
   pkg-owned state (never the user home unless explicitly designed - SOP rule).

## verify.sh (local endpoint health only)

- user exists, .xsession contains the session command
- xrdp active, port listening
- /etc/xrdp/key.pem readable by the xrdp service account
- chrome present when enabled; helpers.rc points at google-chrome when enabled
Cannot prove remote render: E2E gate below does that.

## E2E acceptance (disposable, decision 1)

1. ivps launch a scratch guest on cloudai with tag:incus (name TBD, e.g. xfce-test).
2. Install pkg/xfce on it; capture the printed password.
3. TCP probe from the guacamole test host (cloudai:cloudify) to guest:3389 over the tailnet
   (proves ACL + RDP port before any browser).
4. Configure the test guacamole stack (cloudai:cloudify, already proven by pkg/guacamole
   integration) with RDP_HOST = scratch guest tailnet IP + the generated password.
5. One human browser session (Rachid) renders XFCE + keyboard. That is the acceptance gate.
6. Tear down scratch guest + stack; production untouched.
